---

## 0. 一句话结论

**要分两半看 —— 这两半的答案完全不同：**

| 部分 | Windows | macOS | Linux | 鸿蒙 | 手机 |
| --- | --- | --- | --- | --- | --- |
| **① DSH 插件本体**（`plugin/`，npm 包） | ✅ | ✅ | ✅ | ✅ **理论可行** | △ 取决于客户端 |
| **② 独立小窗进程**（`companion/`） | ✅ | ✅ | ⚠️ 需改脚本 | ❌ **不适用** | ❌ **不适用** |

**核心判据**：插件本体**零平台绑定**（纯 Web 技术），而 companion 是 **Electron 桌面进程**。

## 1. 插件本体：跨平台，且这一点有实测依据

### 1.1 它只依赖四样东西，全都与操作系统无关

| 依赖 | 出处 | 跨平台？ |
| --- | --- | --- |
| `window.__ModuleLoader__.load({id, factory})` | **DSH Host 提供**，不是操作系统提供 | ✅ |
| `<style>` 注入 DOM + `html[data-dsh-mini]` 属性 | 标准 Web API | ✅ |
| `localStorage`（companion 侧用到） | 标准 Web API | ✅ |
| URL 参数 `?dsh-mini=1` | 标准 Web API | ✅ |

### 1.2 实测：源码里零平台分支

对 `plugin/lib/client.js`、`lib/index.js`、`lib/mini-spec.cjs` 全量搜索
`navigator.platform` / `process.platform` / `win32` / `darwin` / `linux`：

```
命中 1 处，且是**注释**：
  client.js:173  // 留白 ⇒ 需要透明窗 ⇒ 透明窗在 Windows 上不能系统缩放
```

⇒ **零平台分支代码**。唯一的 Windows 字样出现在一条解释性注释里。

### 1.3 包声明也印证

```json
"dsh": { "client": { "platform": "web" } }   ← 明确声明为 web 平台
"os" / "cpu": 未声明                          ← npm 层面不限制平台
"dependencies": 零依赖
```

**`platform: "web"` 是关键** —— 它声明的是「运行在浏览器环境」，而不是某个操作系统。

## 2. 官方 DSH 自己的支持范围（权威原文）

### 2.1 官方桌面端 README 原文（第 243 行）

> macOS arm64 命令要求 Apple Silicon。macOS x64 命令可以在 Intel macOS 或带 Rosetta 的
> Apple Silicon 上运行。Windows x64 命令要求 Windows x64。
> **Linux 不是受支持的 Desktop 发布目标。**

### 2.2 结构性证据（三处互相印证）

| 证据 | 内容 |
| --- | --- |
| `apps/desktop/.env.macos.example` | 有 macOS 配置模板 |
| `apps/desktop/.env.windows.example` | 有 Windows 配置模板 |
| **`.env.linux.example`** | **不存在** |
| `electron-builder.config.d.mts` | 只有 `mac`（dmg/notarize）与 `win`（nsis）区块，**没有 `linux`** |
| 打包目标枚举 | `mac-arm64` / `mac-x64` / `win-x64` —— **三项，无 linux** |

⇒ **DSH 官方桌面端 = Windows + macOS，不含 Linux。**

**但注意**：官方不出 Linux 桌面壳 ≠ 插件不能在 Linux 上用。
Linux 上仍有 **CLI（`@deepseek-ai/dsh`）** 与 **Web 前端**（`apps/web`），
而本插件作用于 Web 前端 ⇒ **Linux 上只要能把 DSH 的 Web 界面跑起来，插件就能装能用**。

## 3. 鸿蒙端：能，但有一处需要确认

### 3.1 DSHM（用户自己的鸿蒙客户端）究竟是什么形态

实测其 README 与源码，两条原文：

> （README）**宿主重写，界面不重写。** 界面内容仍是官方 Web 前端；
> ArkUI 侧只承担平台宿主职责

> （`WebApp.ets:6`）authenticatedUrl 后 `BrowserWindow.loadURL` 加载 Host 服务的 web 前端
> （`WebApp.ets:584`）主界面 = Web 壳页：官方 apps/desktop 的鸿蒙等价物（**loadURL → Host web UI**）

⇒ **DSHM 用 ArkWeb WebView 加载官方 Web 前端**，不是用 ArkUI 重写界面。

### 3.2 WebView 能力对照（决定插件能否注入）

`WebApp.ets:2616-2618` 实测配置：

```
Web({ src: this.launchUrl, controller: this.controller })
  .javaScriptAccess(true)      ← JS 可执行
  .domStorageAccess(true)      ← localStorage 可用
```

| Electron 侧（当前 Windows） | ArkWeb 侧（DSHM 鸿蒙） | 是否等价 |
| --- | --- | --- |
| `webview` 标签 + preload | `Web()` + `javaScriptProxy` 桥 | ✅ 都有脚本注入通道 |
| `javaScriptAccess` | `.javaScriptAccess(true)` | ✅ 一致 |
| `domStorageAccess` | `.domStorageAccess(true)` | ✅ 一致 |
| 插件由 Host 经 `/plugins/<id>/client.js` 提供 | **同一套 Host，同一套前端** | ✅ |

**并且 DSHM 本来就在用 `controller.runJavaScript(...)` 注入脚本**（第 2349、2369 行，
用于撤销/重做/剪切等）⇒ **注入通道已被实践证明可用**。

### 3.3 ⇒ 结论

**插件本体在鸿蒙上理论可行**（它加载的就是同一份官方 Web 前端，`__ModuleLoader__` 也在）。
**但有一处我无法在本机验证**：

> **ArkWeb 里 `localStorage` 的 origin 隔离、以及 `__ModuleLoader__` 的模块加载时序**
> 是否与 Chromium 完全一致 —— 需要一台鸿蒙设备实测。

**companion 那半在鸿蒙上完全不适用** —— 它是 Electron 进程，鸿蒙没有 Electron。
DSHM 的「悬浮球 + 小窗」是它**自己用 ArkUI 原生实现**的（README 第 38 行：
「Electron 提供窗口/托盘 → 平台是 ArkUI」）。

## 4. 手机端：取决于客户端，而不是插件

手机上没有 DSH 桌面壳（Electron 不支持手机）。可能的路径：

| 路径 | 插件可用？ | 说明 |
| --- | --- | --- |
| **鸿蒙手机**（走 DSHM） | ✅ 理论可行 | DSHM 明确支持「手机 / 折叠屏 / 平板 / 2in1 共用一份安装包」 |
| **Android / iOS** | ❌ 目前无载体 | 官方无移动端；也未见到第三方移动客户端 |
| **手机浏览器访问桌面端 DSH** | ⚠️ 部分 | 能看到小窗布局，但 `?dsh-mini=1` 是为桌面窗口设计的固定尺寸，手机上不会自适应 |

**最后一个注意点**：本插件的小窗规格（卡片 400×600 / 顶栏 55px / 输入卡 98px）
是**按桌面窗口实测校准**的固定值。在手机竖屏（如 360×800）上，
这些固定值不会自动适配 —— 这不是缺陷，而是**当前设计范围**（目标是桌面小窗）。

## 5. 独立小窗进程（companion）的跨平台结论

### 5.1 好消息：没有 Windows 专有 API

搜索 `thumbarButtons` / `setOverlayIcon` / `flashFrame` / `setAppUserModelId` /
`setSkipTaskbar` / `jumpList` ⇒ **零命中**。

用到的 Electron API 全部跨平台：

```
Tray(8) · BrowserWindow(12) · screen.*(6) · setIgnoreMouseEvents(3)
nativeImage(2) · app.getPath(4) · session.fromPartition(4)
webviewTag(5) · ipcMain(17) · shell.openExternal(1)
```

### 5.2 坏消息：有一处 Windows 专属的**启动方式**

`companion/start.ps1` 是 **PowerShell 脚本**（Windows 专属）。
它的作用只有一个：清掉 `ELECTRON_RUN_AS_NODE` 环境变量污染。

`companion/main.js` 里也有一处 Windows 风格的诊断提示（`Remove-Item Env:\...`）。

⇒ **macOS / Linux 上需要：**
1. 换成对应平台的启动脚本（`start.sh`），或直接 `npx electron .`；
2. 其实 `ELECTRON_RUN_AS_NODE` 污染是**本机 DSH 特有**问题，
   普通用户大概率不需要这个清污步骤。

### 5.3 定位提醒

companion **不随 npm 包发布**（只在 GitHub 仓库的 `companion/`）。所以
「npm 装插件」这件事在任何平台都不受 companion 影响。
