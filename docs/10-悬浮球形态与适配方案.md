# 悬浮球与小窗的「装上就能用」问题 —— 事实核准与适配方案

> 日期：2026-10-11
> 触发：用户质疑「你这不是又开了个 Electron 实例吗？你确定用户装上后就能直接弹出来这个小窗口和悬浮球吗？还有该怎么改才能更广泛地适配？」
> 性质：**只读调查 + 方案**（本轮未改动任何代码）

---

## 0. 先回答那个尖锐的问题：**不能。**

用户的怀疑**完全正确**。实测：

```
npm 包 @a9i5k4/dsh-mini-window@0.1.0 → 只有 6 个文件：
  README.md · cordis.patch.yml · lib/client.js · lib/index.js · lib/mini-spec.cjs · package.json
```

**`companion/` 根本不在包里。** 所以：

| 用户动作 | 实际得到 |
| --- | --- |
| `dsh plugin add @a9i5k4/dsh-mini-window` | ✅ 小窗**模式**（`?dsh-mini=1` 的版面） |
| — | ❌ **没有悬浮球** |
| — | ❌ **没有独立小窗** |
| — | ❌ 装完**不会自动弹出任何东西** |

要看悬浮球，用户还得自己 `git clone` 仓库、`cd companion`、`npm install`（下载 ~380MB 的 Electron）、再 `npm start`。

**这与我 README 里给人的印象不符**（README 把 companion 写成一个平级特性，只在括号里说「不随 npm 包发布」）。
**这是我的表述问题**，必须改。

---

## 1. 为什么会做成这样（我的设计失误）

### 1.1 原始判断

「悬浮球 + 独立浮窗」需要**操作系统级窗口**（无边框、置顶、可拖到屏幕任意位置、任务栏托盘）。
DSH 插件只能改**页面内**的东西 ⇒ 我判断「必须有独立进程」⇒ 选了 Electron。

### 1.2 但这个判断**只对了一半**

我漏掉了一个更简单的事实：**「悬浮球」本身并不需要操作系统窗口。**

它只需要是一个**固定在页面右下角、`position:fixed`、`z-index` 够高的 DOM 元素**。
用户在同一台机器上看着 DSH 界面，球就在界面上 —— 这与操作系统窗口是两回事。

### 1.3 本机就有现成范式（实测）

`@linxin666/dsh-desktop-launcher` 的 description 原文：

> … plus a **floating power button** that exits the host process gracefully.
> **Hot-pluggable — mounted via `~/.dsh/cordis.patch.yml` + a profile node_modules symlink, no dsh source changes.**

它的实现（实测 `lib/client.js`）：

```js
const tag = document.createElement("style");   // 注入 CSS
document.head.appendChild(tag);
// + mountShutdownButton(face) → 挂到 document.body
```

**纯 DOM，零 Electron，装上就有。** 而且它还有一个 `floating-mount.d.ts` 明确把「悬浮按钮」当成一个可复用契约。

⇒ **正确做法就是把悬浮球改成纯 DOM 浮层**，与它同构。

---

## 2. 三条可选路线（附代价与推荐）

| 路线 | 用户装完的体验 | 代价 | 跨平台 |
| --- | --- | --- | --- |
| **A. 纯 DOM 悬浮球**（推荐） | 打开 DSH 界面右下角**就有球**，点一下在小窗/大窗之间切 | 球在**页面内**，不能拖出浏览器、不能常驻在 DSH 关闭后 | ✅ 全平台（Web 技术） |
| **B. 保持 Electron 进程** | 装了 npm 包**什么都没有**，需另装 companion | 380MB Electron、要用户手动跑脚本 | ❌ 仅桌面 |
| **C. A + B 并存** | 默认 A（开箱即用）；想要"真·桌面浮窗"再装 companion | 维护两套 | A 全平台 / B 桌面 |

**推荐 A，把 B 降级为可选增强。**

理由：
1. **A 真正做到「装上就弹出来」** —— 这是用户的核心诉求；
2. **A 跨平台**（包括将来可能的 Web 部署）—— 直接解决「更广泛适配」；
3. **A 零体积**（现在插件包只有 22KB）；
4. B 的价值（球在页面外、DSH 关了还在）是**少数场景**，不值得为它让全体用户付 380MB。

---

## 3. 路线 A 的技术方案（已确认可行，有本机先例）

### 3.1 前端（`plugin/lib/client.js`）

```
① 注入 CSS：position:fixed; right:20px; bottom:20px; z-index:9999; border-radius:50%
② 挂 DOM：document.body.appendChild(ballEl)   ← 与 desktop-launcher 同构
③ 点击行为：切换 ?dsh-mini=1 视图（或直接开小窗模式）
④ 拖动：pointerdown/move/up 改 left/top，松手吸附边缘（纯前端）
⑤ 只用 SVG 自绘图标，不依赖任何图片资源
```

已有基础设施可复用：本项目 `panel.js` 里那套「悬浮球拖动 + 吸附边缘」逻辑可以直接搬过来
（现在是 Electron 渲染进程里跑的，本身就是标准 DOM 代码）。

### 3.2 host 侧（`plugin/lib/index.js`）—— **只在需要跨进程时才用**

若要让球触发「真·独立窗口」，host 侧需要一个进程管理端点。本机已有权威范式：

```js
const inject = ['webServer', 'systemPrompt'];     // ← 实测自 dsh-desktop-launcher
import type { WebRoute } from '@deepseek-ai/dsh-host-webserver';
// 注册 /api/dsh-mini-window/<action> 路由（必须带 loopback-only 信任围栏）
```

**注意**：这会让插件**不再零依赖**（要 peer `@deepseek-ai/dsh-host-webserver`）。
所以路线 A 应当**不碰 host 侧**，保持现在的零依赖。

### 3.3 默认行为（关键的产品决策）

装完插件后，球是**一直显示**还是**要手动开**？

| 选项 | 说明 |
| --- | --- |
| **默认显示** | 「装上就弹出来」最直接，但会在所有用户的界面上多一个球 |
| 默认隐藏 + 设置里开 | 更克制，但用户找不到 |
| **默认显示 + 设置里可关**（建议） | 兼顾，且遵循「负路径可验证」的既有习惯 |

## 4. 跨平台适配清单（针对用户「更广泛适配」的诉求）

### 4.1 插件本体（已基本达标）

| 项 | 现状 | 需要做 |
| --- | --- | --- |
| 平台绑定 | ✅ 零（实测只有 1 处注释提到 Windows） | — |
| 依赖 | ✅ 零运行时依赖 | 若加 host 路由则会引入 1 个 peer，需权衡 |
| 启动脚本 | ⚠️ `companion/start.ps1` 是 Windows 专属 | **加 `start.sh`** 或改用 `npm start`（跨平台） |

### 4.2 若要支持 Linux（官方不出 Linux 桌面壳）

用户仍可用 **CLI + 浏览器**访问 DSH Web 界面 ⇒ **插件可用**。
但需要确认：`dsh` CLI 在 Linux 上起 Web 服务是否是一等公民路径（README 里官方未强调）。

### 4.3 手机 / 触屏

当前规格（卡片 400×600、顶栏 55、输入卡 98）是**桌面固定值**。
若要触屏可用，需要：
- 触控目标 ≥ 44px（现在顶栏按钮 28px）
- 悬浮球支持触摸拖动（`pointerdown` 已覆盖触屏，但要测）
- 或干脆在窄屏下**不注入**小窗样式（让官方响应式接管）

## 5. 结论与建议的下一步

**用户的两个质疑都成立**，需要改的是**产品形态**，不只是文档：

1. **把悬浮球改成纯 DOM 浮层**（路线 A）—— 这是「装上就能用」的唯一办法；
2. **README 如实写清**：npm 包装上后得到什么、companion 是可选的另一种选择；
3. 若要保留 Electron 版，把它定位为「**可选增强**」，并在 README 里说明它带来什么额外能力。

**建议执行顺序**：
1. 先做 A 的悬浮球（纯 DOM，改动集中在 `client.js`）
2. 改 README 的支持矩阵与「你装完会看到什么」
3. 再考虑 host 侧路由 + 可选 Electron 增强

## 6. 诚实边界

| 结论 | 证据等级 |
| --- | --- |
| npm 包不含 companion | **实测**（`npm pack --dry-run` 文件清单） |
| desktop-launcher 用纯 DOM 做悬浮按钮 | **实测**（读其 description 与 client.js 源码） |
| host 侧插件注入 `webServer` 注册路由 | **实测**（读其 `inject = ['webServer','systemPrompt']` 与 `WebRoute` 类型导入） |
| 路线 A 能实现「装上就有球」 | **强推断**（有同构先例 + 本项目已有拖动逻辑） |
| 纯 DOM 球能替代 Electron 版全部能力 | **不能** —— 球在页面内，DSH 窗口关了球就没了；这是能力差异，非实现差异 |
